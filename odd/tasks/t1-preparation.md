S5. Standing limits: work on `main`, no new branch; commits only with explicit authorization; nothing pushed. `docs/prd-backend.md` §9 still says the split is not authorization to begin implementation, so S1 itself stays unauthorized until the user says otherwise.

L8. T1.3 closed. Design written to `docs/design-identity-ddl.md`, read first through `.agents/skills/database-postgres-patterns/SKILL.md`. The platform actors `ADMIN`/`SOPORTE` are `account.platform_role`, not memberships, which is why the auth design's `ctx` claim is absent for them. `OWNER` is business-wide (`branch_id NULL`), `EMPLOYEE` branch-scoped, enforced by `CHECK` plus a composite foreign key so a membership cannot point at another business's branch. Evidence: both migrations applied to a throwaway PostgreSQL 17 container, 14 falsification cases all matching their expectation (same email for both account kinds allowed; `(email, kind)` duplicate refused; `CUSTOMER` with `platform_role` refused; both wrong role/branch shapes refused; cross-business branch refused; duplicate active owner refused; re-adding a revoked owner allowed), `EXPLAIN` showing `Index Scan using membership_guard_idx` with no sequential scan, two concurrent refresh exchanges producing **exactly one winner**, reuse of a rotated token inserting nothing, family revocation revoking the family in one statement, and both `Down` blocks leaving zero tables and zero `schema_%` schemas.
