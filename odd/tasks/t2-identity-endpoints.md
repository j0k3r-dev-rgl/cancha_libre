L4. Scope derivation, so no route is invented: S1 delivers `BE-ACC-01…07`, `BE-ORG-01` (minimum spine), `BE-ENG-01/05`, and closes `AC-18`, `AC-26`, `AC-42` (partial), `AC-43`. No product decision is required to derive the inventory.
L5. T2.1–T2.4 drafted into `docs/design-identity-endpoints.md` and the roadmap §5.2 inventory. Two behaviours were **verified instead of assumed**, in a throwaway Go module using the pinned huma v2.39.1 (module removed afterwards, nothing written to `core/`):
- `huma.NewError` is an overridable `var`, and the override reaches the wire (`403`, `application/problem+json`, `type = urn:canchalibre:error:forbidden`).
- **`Errors: []int` does NOT publish the `type`**: `defineErrors` expands every code from one `huma.NewError(0, "")` example, so the contract shows a single generic schema. Declaring the error as an explicit `Responses` entry with a per-error `Example` **does** carry the URN into the generated YAML. This became a task-level rule for S1 rather than a footnote, because the opposite is the easy assumption and it would have shipped a contract whose `type` was never documented.
- The fallback works and distinguishes correctly: routed `GET` → 200; wrong method on a real route → **405** with `method-not-allowed`; unrouted path → **404** with `not-found`, both `application/problem+json` (previously `text/plain`).
L6. Deliberate boundaries recorded rather than silently resolved: business/branch creation is S2 and S1 ships no business-creation route (the roadmap already forbids S1 from growing into branch management); `SOPORTE` is provisioned, never self-served, and its phone/DNI procedures are S4; `POST /auth/refresh` is documented **non-idempotent** on purpose, because a replayed refresh is the T1.2 D6 reuse signal and not a retry to absorb; `pgx/v5` and `goose` stay out of this block (build-time work, S1).
L7. **Defect found by my own mechanical cross-check, and fixed.** The inventory rows originally wrote the error column with shorthand slugs (`400 validation`) while the design doc's catalog defines full URNs (`urn:canchalibre:error:validation`). Two tables in different files were therefore describing the same contract in two vocabularies, and the roadmap row alone could not be checked against the catalog. Fixed by stating the slug→URN mapping explicitly next to the inventory (`403 forbidden` ⇒ `type = urn:canchalibre:error:forbidden`), which makes a row machine-checkable against §1.1. A first edit attempt of mine also glued a table separator onto the `login` row; caught by grepping for `||` on a line and repaired before it shipped.
L8. Identifiers audited mechanically, not by eye: every `BE-*` and `AC-*` cited in the inventory was cross-checked against the PRD §4 tables and the `mvp.md` acceptance table — **30 `BE-*` and 48 `AC-*` citations, zero invented**, and no cited identifier is missing. Every slug used by an endpoint row exists in the catalog (`used ⊆ defined`). The only catalog entries not used by an endpoint row are `method-not-allowed` and `unsupported-media-type`; the first is the `MethodNotAllowed` fallback, and the second is emitted by huma's own `Content-Type` negotiation rather than by a fallback handler, so body-accepting operations declare it (design doc §1.3).
L9. Two findings from my own follow-up probe, both turned into rules because each silently breaks D1 (`never about:blank`):
- **A status the override does not map leaks `about:blank`.** An override mapping only `404` returned `type = "about:blank"` for `huma.NewError(422, …)`. So the override must be **total and fail closed** (unmapped → `urn:canchalibre:error:internal`), not partial.
- **`415` is reachable without any endpoint declaring it.** `POST` with `Content-Type: text/plain` returned `415` and the operation's contract did **not** declare `415`. So each body-accepting operation must declare it explicitly, or its contract omits a refusal it actually performs. This also answers the verification advisory that called the 415 catalog row unused: it was reachable, the catalog was right, and the inventory needed the rule.
L10. Verification advisory about missing `AC-*` on four rows (`refresh`, `requestPasswordRecovery`, `resetPassword`, `logout`): `—` is correct and now says so explicitly in the inventory. The MVP's acceptance table has no criterion for session refresh, token-based recovery or logout, because those are engineering obligations of `BE-ACC-01` rather than customer-visible acceptance examples. Inventing an AC to fill the cell would have been a fabricated requirement; `BE-ACC-01` is cited instead, and the inventory states that `—` means "no acceptance criterion in the MVP covers this, deliberately".

Each task above records the commit by that range rather than by its own hash, deliberately: a commit cannot contain its own hash, and amending to insert it would only move the target again.
